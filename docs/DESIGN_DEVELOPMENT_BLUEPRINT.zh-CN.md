# CopilotMail 设计开发蓝图

> 状态：**P0–P2 的界面切片已完成源码收敛与本地前端全量回归；P3 已有首个真实的
> 精确 Agent 发件证据契约，运行与执行观测仍等待独立契约**。
> 本文补充而不替代
> [`DESIGN.md`](../DESIGN.md) 的现行约束；在实现开始前，不把规划中的模块、状态或
> 素材伪装成已上线能力。

## 1. 这次要解决的问题

CopilotMail 不是把“邮箱”和“Agent 面板”摆在同一个壳里。它是公司内部的通用通信
系统：Human 与 Agent 都是独立、可授权、可追责的主体；邮件、域名、审批和审计则是
它们共同操作的企业资源。

新版体验的最低目标是让操作者在任何关键界面都能在数秒内回答四个问题：

1. **谁在操作？** Human、Agent、Service，或经真实授权的委托主体。
2. **作用于什么范围？** 当前组织、邮箱、域名、归档或审批请求。
3. **结果是否可信？** 已确认、等待证据、需要人工复核，还是未知写入。
4. **下一步是什么？** 只显示当前权限和真实后端状态允许的一个主动作。

为此，本蓝图将设计方向命名为 **Calm Evidence Workspace / 静默证据工作台**：
高密度但安静，优先呈现事实、边界与证据，而不依靠营销式大图、彩色卡片或机器人
装饰制造“AI 感”。

## 2. 参考如何被抽象，而不是被复制

本次参考了 [getdesign.md 的 Linear 分析](https://getdesign.md/linear.app/design-md) 与
[Agent Mail](https://agent.qq.com/) 的可观察设计语言，但不会复制其页面、Logo、文案、
配色、二维码、机器人轮廓或交互流程。

| 参考 | 取用的方法 | 明确不取用的内容 |
| --- | --- | --- |
| getdesign.md / Linear | 克制信息密度、细边框、单一交互强调色、明确层级、少而精的主操作 | 近黑营销画布、紫色品牌、原页面布局、动效和文案 |
| Agent Mail | 暖白底、黑色圆角线性图形、主视觉的单一叙事焦点、低噪音登录感 | QQ/腾讯品牌、QR 登录结构、任何吉祥物、机器人脸或人像 |

因此，CopilotMail 保持现有“暖纸 + 白表面 + 墨黑 + 深靛蓝信号”的 token 契约。
靛蓝只表示当前焦点、真实 Agent 相关语义或可执行主操作；成功、警告、失败仍只能
表示有后端事实支持的状态。模块间通过结构、留白和排版分层，**不通过无意义的颜色
拼接或大面积状态底色分层**。

## 3. 不可破坏的设计边界

本蓝图继承以下硬约束；任何开发模型都不能用视觉效果绕过它们。

- 不显示 API 未提供的 Agent Owner、Scope、在线、执行、委托、邮箱、收件人、投递明细或
  审批结果；不从地址推断。P3 已有的精确发件证据只能按其脱敏准入/批准、可选投递聚合和
  审计引用语义呈现，不能扩大解释。
- 不用 Human / Agent 全局切换开关混淆身份与工作意图。Human 使用网页完成任务；Agent
  的一等公民入口是 API、SDK 和事件协议。
- 不出现 lorem ipsum、假头像、假指标、死按钮、永久骨架、无动作卡片、通用空态、
  彩虹/渐变拼色、玻璃拟态、霓虹光晕或背景粒子。
- 不用生成式位图作为功能图标、按钮、图表、文字图形或导航标识。功能图标继续由原创
  SVG 注册表提供。
- 未知写入一律冻结变更入口，只保留精确读取/对账；不得将“网络错误”设计成可以盲目
  再提交的普通失败。
- 高风险动作必须显示真实对象、影响、执行主体、审批/理由边界和可追溯结果；按钮不能
  只写“确定”或“继续”。

## 4. 三个一等公民入口

不要把 Agent 伪装成一个会点击网页的 Human。产品用三个有边界的入口服务不同任务：

```text
CopilotMail
├─ Human Mail Workspace
│  ├─ 当前邮箱范围、收件箱、搜索、阅读、写信、草稿、已发送
│  └─ Human / Agent / Shared / Group 邮箱的真实身份与权限状态
├─ Human Control Plane
│  ├─ 指挥台
│  ├─ 执行与审核：邮件域名、审批、案件、Legal Hold
│  ├─ 证据与留存：审计、保留
│  └─ 身份与自动化：Agent 检视、角色访问
└─ Agent Client Surface
   ├─ 版本化 API、SDK、Scope Token、CAS 与 Idempotency
   ├─ 结构化错误、订阅/Claim/Lease/Ack/Nack
   └─ 事件、审批和审计证据；不是“聊天式 Agent 操作台”
```

### 4.1 Human Mail Workspace

保留现有的三栏效率结构，而不是重做成仪表盘：

```text
[ 邮箱范围 Rail ] [ 消息队列 ] [ 阅读 / 写信区 ] [ 按需 Evidence Inspector ]
```

- Rail 显示当前授权的邮箱范围和清晰的身份标签；不能用颜色代替 `Human`、`Agent`、
  `Shared`、`Group` 文本。
- 队列服务扫描：发件人、主题、时间、未读、附件和当前真实风险提示。它不承担治理历史。
- 阅读/写信区服务任务完成：一项主操作、少量可执行动作、可理解的草稿/提交/投递状态。
- 只有服务端提供 actor、委托、策略或投递证据时，才显示第四个默认收起的 Inspector。
- ≥1084px 使用完整三栏；1008–1083px 使用仍有文字的紧凑 rail，确保 Queue 与 Reading
  可读；≤1007px 维持显式列表—详情栈与 44×44px 触点，不将三栏硬压成三条窄缝。

### 4.2 Human Control Plane

管理端从“九个平级工具按钮”收敛为带清晰意图的四组导航。Desktop 保留文字标签与
`aria-current`；移动端改为当前页面标题 + 分组抽屉，避免五行导航吞掉首屏。

| 分组 | 页面 | 核心问题 |
| --- | --- | --- |
| 指挥台 | Overview | 今天需要确认什么、哪些风险需要人接管？ |
| 执行与审核 | Mail domains、Approvals、Cases、Legal holds | 资源是否可安全改变，是否需要我作决定？ |
| 证据与留存 | Audit、Retention | 我如何复核一个事件、导出或留存？ |
| 身份与自动化 | Agent inspector、Roles | 谁拥有何种能力，证据来自哪里？ |

每个管理页面顶部统一使用 **Context Bar**，只显示真实字段：组织、资源、主体、最后
确认时间、当前状态/风险、一个主动作。它不是 KPI 横幅，也不包含虚构的运行指标。

详情页遵循“**事实 → 决策 → 证据**”而不是“表单卡片堆叠”：

1. 事实区：资源状态、版本、范围和最近观测。
2. 决策区：唯一可执行主动作、条件、影响和确认方式。
3. 证据区：审批、Actor、Request/Trace ID、不可变时间线；桌面可折叠为右侧 Inspector。

### 4.3 Agent Client Surface

Agent 的体验是确定性而非拟人化：请求规范、Scope、版本、Idempotency、CAS、结构化错误
和 Audit/Outbox 证据。网页中的 Agent Inspector 展示受控控制面快照；P3 只在该 Agent
已被精确确认后，允许 Human 再输入一个 submission UUID 读取最小的发件证据。两者都不能
把“最近控制面记录”渲染成心跳、在线或执行成功。

P3 的读取固定为
`POST /api/v2/agents/{agent_id}/mail-submissions/{submission_id}/evidence`。它仅面向同时具有
`identity.manage` 与 `audit.read` 的 Active Human；受限 bearer 还需带两个同名 scope。它在
业务语义上仍是精确读取，却必须以 `POST` 执行：成功观测会原子追加 High Audit/Outbox，
Admin Cookie 因而走既有 Origin/CSRF guard，页面不得预取、轮询或自动重放。响应只含提交
状态/时间、不可变准入与策略批准引用、可选最新投递**聚合**和最小审计引用。它不是目录、
投递成功断言、运行/执行/委托视图，也不携带邮箱、收件人、SMTP/提供方或正文。管理端默认
收起审计引用，并在 `404` 时统一隐藏缺失、跨租户、主体类型、双 UUID 关系和 production
准入失败的具体原因。

证据时间遵循 PostgreSQL 的来源事实，而不是 UI 排序：请求/准入/终态审计分别绑定提交创建、
准入和精确终态动作；策略/批准只在当时有效才可证明历史准入。初始 pending intent 的
`updated_at` 不是其后 `admitted_at` 的上界；内部 `accepted_at` 只用于将可选投递聚合因果
绑定到接受之后，不能被渲染成额外的人类可见“已送达”时间。

未来只有在后端提供相应字段时，Agent 详情才可增加下列内容：

| 计划表达 | 所需真实契约 |
| --- | --- |
| 代表谁执行 | actor、`on_behalf_of`、委托有效期 |
| 处理轨迹 | execution ID、阶段、原因、重试/接管状态 |
| 完整策略阻断/审批 | decision、拒绝原因、可执行下一步及其授权边界 |
| 收件人级投递证据 | 最小化 delivery trace、协议/提供方证据与单独隐私评审 |

没有这些字段就没有对应 Tab、卡片或“即将推出”占位。

## 5. 统一的状态、风险与证据语言

每个关键状态使用同一四元结构，避免不同页面创造各自的状态语法：

```text
状态（发生了什么） + 证据（依据是什么） + 约束（现在不能做什么） + 下一步（能做什么）
```

| 领域 | 必须分开的真实状态 | 页面设计要求 |
| --- | --- | --- |
| 邮件 | 草稿、已接受、对账中、人工复核、投递、失败、未知提交 | 不把已接受写成已投递；未知提交冻结写信并引导读取对账 |
| 审批 | Pending、Approved、Rejected、Cancelled、Expired、Executed | 先呈现决策影响，再呈现不可变步骤和 Actor |
| 域名 | 注册、DNS verified、Control-plane active、Engine pending/ready/failed | 生命周期、DNS 证据、路由版本和引擎投影分层显示 |
| 审计导出 | 需双人批准、Grant 有效、Grant 已过期、下载已记账 | 授权与下载是两个高风险步骤，不能表现为普通附件下载 |
| Agent | 生命周期、真实 Owner、Scope 交集、控制面观测 | 不使用“在线”“运行中”等无契约词汇 |
| Agent 发件证据 | 精确提交状态、准入/批准、可选最新投递聚合、审计引用 | `delivery=null` 仅表示本响应无快照；审计引用默认收起，不从聚合推出投递成功或运行状态 |

状态芯片不是彩色糖果：它必须同时有语义图形、可见本地化文本、时间或证据引用。
颜色只作第三层冗余信息。一次性 Token、凭证明文、邮件内容、附件和敏感 Trace 不进入
URL、历史、静态提示、统计卡或插画。

## 6. 视觉与组件规格

### 6.1 Token 和排版

实现必须继续消费 `web/design-system/src/styles.css` 的现有 `--cm-*` 语义 token，功能
CSS 不新增原始颜色。Token 的语义分工如下：

| 层级 | 用法 |
| --- | --- |
| Canvas / Surface / Line | 暖白画布、阅读/数据表面、细分隔线；建立大部分层级 |
| Ink / Muted | 正文、元数据、证据说明；阅读优先于装饰 |
| Agent signal | 当前焦点、选中、真实 Agent 相关信息；不能大面积铺底 |
| Positive / Warning / Critical / Info | 已确认完成、需处理、失败/破坏性、系统说明；必须配合文字/图形 |

- UI 字体使用现有系统 sans/Inter 路径；等宽字体仅用于 ID、哈希、版本、快捷键和证据。
- 桌面页面标题采用 20–24px，模块标题 14–16px，正文以 14px/20px 为准；邮件正文可以
  提升至 15–16px/24px 以保留阅读舒适度。
- 继续使用 8px 级距、6–8px 控件圆角、10–12px 面板圆角和克制单层阴影。表格、队列
  与时间线优先用细分隔线，而不是给每一项加重阴影卡片。
- Dark mode 只能从同一 token 语义推导；不是当前工作范围，也不能成为引入第二套视觉
  语言的借口。

### 6.2 图标语言

图标保留现有原创 SVG registry，按以下规则扩展：

| 规则 | 标准 |
| --- | --- |
| 画布与笔触 | 24×24 `viewBox`、1.75px 描边、圆角端点/连接、`currentColor` |
| Human | 圆形身份边界 + 单一内轴；必须有可见 `Human`/姓名文本 |
| Agent | 圆角执行核心 + 三条执行轨；必须有可见 `Agent` 及真实 Owner/Scope（若存在） |
| 邮件/域名/审计 | 信封、路由节点、证据环/时间线分别表示对象；不混用品牌 Logo |
| 危险动词 | 导出、暂停、吊销、删除总是“图标 + 动词文字 + 确认语义”，不能只给图标 |
| 可访问性 | 装饰 SVG 为 `aria-hidden`；独立图标按钮必须有当前语言下的可访问名称 |

#### 图标命名与对象地图

新图标只能先加入 shared registry，再由应用消费；命名采用“领域-对象/动词”，避免在
业务页面内复制一段 path。以下是后续实现应覆盖的最小语义集合：

| 族 | 建议名称 | 视觉语法 | 使用边界 |
| --- | --- | --- | --- |
| 主体 | `identity-human` | 圆形边界 + 内轴 | 只与名称/`Human` 文本一起出现 |
| 主体 | `identity-agent` | 圆角核心 + 三条执行轨 | 只与名称/`Agent` 和真实范围一起出现 |
| 主体 | `identity-shared` / `identity-group` / `identity-service` | 双托盘 / 路由节点 / 受界核心 | 不取代任何持久化主体的文字名称 |
| 邮件 | `mail-inbox` / `mail-compose` / `mail-reply` / `mail-send` | 信封与方向线，方向一眼可辨 | 只有已实现动词才进入工具栏 |
| 治理 | `govern-domain` / `govern-route` / `govern-approval` / `govern-hold` | 节点、路线、双人确认、封存边界 | 不把品牌或“安全感”图标滥用于普通导航 |
| 证据 | `evidence-audit` / `evidence-export` / `evidence-retention` | 时间环、出站受控箭头、留存容器 | Export 永远配合批准/有效期文字 |
| 状态 | `status-confirmed` / `status-review` / `status-blocked` / `status-unknown` | 勾选环、待审节点、边界/锁、问号环 | 状态始终同时有可见文字和事实来源 |

禁止 emoji、彩色贴纸、3D 图标、不同线宽的第三方图标混搭和生成位图缩放为 16px 图标。

### 6.3 计划新增的共享组件

这些组件是实现任务，而不是现在应渲染的空壳；每一个都必须由真实 DTO 驱动。

| 组件 | 用途 | 数据/安全边界 |
| --- | --- | --- |
| `ContextBar` | 组织、资源、主体、状态、最后确认、唯一主操作 | 字段必须来自当前页面已授权读取 |
| `EvidenceInspector` | 审批/Actor/版本/Request ID/不可变时间线 | 默认收起；不保存敏感证据到本地 |
| `LifecycleStage` | 域名和审批的已确认阶段 | 不推测下一阶段，不将 engine projection 混入生命周期 |
| `RiskConfirmation` | 导出、暂停、路由、授权等高风险确认 | 显示真实对象、影响、理由/审批；关闭后回焦点 |
| `UnknownWriteLock` | 未知写入后的冻结/对账说明 | 禁止更改输入或换一个请求重发；仅调用契约定义的精确读取（通常为 GET，写读取审计的证据观察为受 Origin/CSRF 保护的 POST） |
| `AuditTimeline` | 事件、主体、动作、时间、证据引用 | 未授权/被最小化字段不渲染 |
| `AdaptiveNavDrawer` | 窄屏控制面分组导航 | 保留文字、当前页和键盘焦点，不改动授权 |

## 8. 核心页面样板与实现顺序

### 8.1 页面样板

以下是实现时应保持的内容优先级。它们是布局决策，不是可以直接出现在生产页面的
占位 wireframe；每个字段仍要由已授权的真实响应填充。

#### Human Mail：阅读优先、范围持续可见

```text
┌ Scope rail ───────┬ Queue ──────────────────────┬ Reading / Compose ───────────────┐
│ 当前邮箱 + 身份    │ 搜索、真实筛选、消息行       │ 身份/收件范围 + 一个主操作        │
│ 文件夹/导航        │ 发件人、主题、时间、风险     │ 正文或编辑器 + 已知提交状态        │
│ 会话/退出          │                              │ [证据 Inspector 仅按需展开]        │
└────────────────────┴──────────────────────────────┴───────────────────────────────────┘
```

- 写信的 `From`、只读性和提交状态必须紧邻主操作，而不是隐藏在溢出菜单。
- Agent 邮箱选择后，队列和详情请求都绑定到该精确邮箱；图标不替代可见身份说明。
- 草稿、投递、人工复核和未知提交使用第 5 节的四元状态结构，不能被成功 Toast 覆盖。

#### Approval：先判断影响，再作决定

```text
Context Bar: 组织 / 当前筛选 / 已确认时间                         [唯一主动作]
┌ Decision queue ──────────────┬ Decision detail ──────────────┬ Evidence (可折叠) ┐
│ 待我决定 / 我的申请            │ 资源与风险摘要                 │ 审批步骤、主体、时间       │
│ 真实状态、到期、资源标签        │ Approve / Reject / Cancel 条件 │ 策略键、Request/Trace      │
│ 不渲染虚构优先级或 SLA          │ 理由、确认、未知写入锁定        │ 不可变审计链接             │
└───────────────────────────────┴──────────────────────────────┴─────────────────────────┘
```

- 第一个阅读块是“此决定会改变什么”，不是原始 UUID 或表单字段。
- 对未知决策/取消写入，详情停留在原资源与精确命令上，只允许读取对账；不创建第二个按钮。

#### Mail Domain：状态机而不是一大张配置表

```text
Context Bar: 域名 / 生命周期 / Route version / 最近观测            [当前阶段主动作]
Facts:  Ownership → DNS evidence → Explicit activation → Engine projection
Decision: 该阶段的唯一表单 / 明确预期版本 / 显式确认
Evidence: challenge 时间、DNS 结果、Actor、Outbox projection、审计引用
```

- DNS `verified`、控制平面 `active`、邮件引擎 `ready` 必须分行呈现；三者不能共用一个
  “已就绪”标签。
- 一次性 ownership token 只在产生它的当前 Dialog 内显示；关闭、导航或主体变化即清除。
- Route 更新将当前版本与操作者期望版本并列；CAS 冲突或未知写入都只允许重新读取。

#### Audit：检索与导出是两件事

```text
Query context: 时间范围 / 真实筛选 / 结果范围
┌ Results queue ────────────────┬ Evidence detail ─────────────────────────────────────────┐
│ 事件、主体、动作、目标、时间   │ 事件事实、最小化上下文、哈希/归档/审批链接              │
│ 过滤只来自 server contract     │ Export authorization（独立且默认收起的高风险安全门）     │
└───────────────────────────────┴──────────────────────────────────────────────────────────┘
```

- 导出流程严格为：双人审批事实 → 有效 Grant → 精确对象版本下载 → 下载审计；不能表现为
  “点击一下载就完成”。
- `audit-evidence-chain-v2` 只能在第 7 节说明的首次、有权限、无当前 Grant 的状态使用，
  并与真实输入和说明同屏。

#### Agent Inspector：受控快照，不是运行大屏

```text
明确 Agent UUID → 已授权读取 → 身份 / Owner / Scope 交集 / 控制面观测 / 最近确认
                                 └→ 明确 submission UUID → 准入 / 批准 / 可选投递聚合
                                                          └→ 默认收起的审计引用
```

- 没有 UUID 时显示输入与说明，不使用假 Agent 列表、假头像或“在线”统计。
- Snapshot 仅陈述服务端实际返回的控制面记录；刷新失败保留上次确认快照并标明其时间。
- P3 发件证据只针对当前 Agent 的第二个、显式规范 UUID；它不建立提交目录，也不在没有
  submission ID 时渲染空态卡片。`delivery=null` 只表示本响应没有投递快照，审计引用由
  `EvidenceInspector` 默认收起，不能把聚合计数解释成收件人明细或投递成功。触发按钮是
  明确的“读取并记账”`POST`，不使用 GET 预读或自动重放；Cookie 会话沿用 Origin/CSRF
  防护。
- Agent 的 API/SDK 层仍是日常操作入口；网页只提供 Human 的理解、监督和必要接管面。

### P0 — 共享基础和壳层

1. 把 Context Bar、状态/证据/风险原语纳入 shared design system。
2. 以分组导航重构 Admin shell；保留现有路由、会话重校验、焦点恢复和移动端 44px 触点。
3. 将 master-detail 的“阅读态”与“操作检查器态”分开：需要生命周期/路由编辑时可扩至
   380–440px，阅读态再收敛，不让长表单挤成窄列。

### P1 — 日常工作与关键决策

1. **Human Mail Workspace：** 在不改变现有安全状态机前提下补齐稳定的身份/范围/提交
   上下文；保持三栏效率模型。
2. **Approval Command Center：** 分离“待我决定”和“我的申请”；详情顺序为决策摘要、
   风险与资源、不可变步骤/证据。
3. **Mail Domain Lifecycle：** 将注册 → DNS 证据 → 显式启用 → 引擎投影呈现为真实阶段，
   每个阶段最多一个主动作；一次性 token 规则不变。

### P2 — 证据、留存与受控观察

1. **Audit Investigation：** 查询条件 → 结果队列 → 证据详情；导出授权是独立安全门，
   而不是普通下载按钮。
2. **Agent Control Plane：** 当前只组织已实现的单 Agent 快照；按照身份、Owner、授权
   交集、控制面记录、观测时间呈现，不制造运行大屏。
3. **Cases / Holds / Roles / Retention：** 从审批、审计和域名详情建立受控深链；没有事实
   关联就不展示“相关项”。

本阶段只消费现有、可精确读取的 DTO 与写入契约：未知写入冻结、证据默认收起和
Human/Agent 的不同操作边界继续生效。它不为尚不存在的 Agent execution、委托、运行
遥测、完整策略决策或收件人级投递证据制造预留卡片、假状态或虚构入口。

### P3 — 已确定的精确发件证据与条件扩展

本轮 P3 的第一个真实契约已经限定为一个 Human-only 的精确读取：同一操作者必须提供
Agent UUID 与 submission UUID，且拥有 `identity.manage`、`audit.read` 和 Active Human
资格。它采用 `POST`，因为成功读取本身会同事务写入受治理审计和 Outbox；Admin Cookie
沿用 Origin/CSRF 保护。页面的最小结构固定为提交事实 → 准入/批准事实 → 可选最新投递
聚合 → 默认收起的审计引用；`404` 不区分目标缺失、跨租户、双 ID 不匹配或 production
准入缺失。

时间线只用 PostgreSQL 的请求、准入、策略/批准、终态和投递来源事实：请求/准入审计与
相应业务时间精确相等，终态审计与精确动作绑定；迟到批准不能使早先准入“事后合法”。
准入允许晚于初始 intent `updated_at`，而不公开的 `accepted_at` 只约束投递因果。读取
Audit/Outbox 与该次响应的 `observed_at` 及最小返回事实绑定，任何一项无法提交都不返回结果。

它不证明 Agent 运行、执行、委托、邮箱访问、收件人身份、SMTP/提供方行为、正文内容或
投递成功。只有后端另行提供并完成留存、访问控制、审计和隐私评审后，才扩展 execution、
委托、完整策略决策或收件人级投递证据；无数据时不放预留模块。

## 9. 响应式、无障碍和国际化

| 宽度 | 行为 |
| --- | --- |
| ≥ 1280px | 完整 Rail + list/queue + detail；Evidence Inspector 按需打开 |
| 1084–1279px | 完整文字 rail、328–400px Queue 与至少 520px 阅读区 |
| 1008–1083px | 160px 文字 rail、328px Queue 与至少 520px 阅读区 |
| ≤1007px | Mail 进入显式列表—详情；Control Plane 保持列表—详情互斥 |
| ≤ 720px | Admin 采用当前页面标题 + 分组抽屉；详情单列并有明确返回 |
| ≤ 390px | 所有关键触点至少 44×44px，风险动作保留文字，不只藏在图标菜单 |

必须继续满足：

- WCAG 2.2 AA 对比度、双层可见焦点、`prefers-reduced-motion`、Dialog 焦点圈闭与关闭
  后回焦点；
- 图标不承担唯一语义，表格有语义表头/`caption`，复杂证据有文本摘要；
- 所有用户文案进入现有中英 typed i18n catalog；中文短句和英文动作动词分别校对；
- 全部核心页面在 1440、1280、1024、768、390px，以中英、长文本、空/错误/只读/未知写入
  等真实状态完成截图与键盘回归。

## 10. 交付与验收矩阵

本蓝图的每个实施切片都按以下矩阵验收；设计资产和代码不得把规划中的能力伪装为
已上线状态。

| 交付项 | 完成证据 | 失败即拒绝的情况 |
| --- | --- | --- |
| Token/组件 | shared design-system 导出、类型/单元测试 | feature CSS 原始色值、私有图标/原语分叉 |
| 信息架构 | 分组导航、Context Bar、焦点/窄屏回归 | 只保留图标、移动端首屏被导航占满、改变现有授权语义 |
| 页面流程 | 真实 API 夹具、状态矩阵、E2E | 假数据、死按钮、把 unknown write 当普通错误重试 |
| Human/Agent | 身份 + 文字 + 真实范围/证据 | 从地址推断 Agent、拟人化 Agent 或全局身份开关 |
| 素材 | manifest 哈希、Alt、单一场景映射、WebP 预算 | 未登记位图、伪 UI/文字/Logo、通用万能空态 |
| 无障碍/语言 | Axe、键盘、焦点、中文/英文截图 | 颜色唯一语义、仅 hover 操作、未本地化字符串 |
| 回归 | `check_design_governance`、`check_web_i18n`、TypeScript、Vitest、build、Playwright | 放宽视觉阈值、自动接受快照、未人工审图 |

## 11. 实施启动规则

无论由何种开发模型实施，开发方必须先提交 P0 的可审阅切片，而不是同时改完所有页面：

1. 复核本文、`DESIGN.md`、现有 API/状态机和现有截图基线；
2. 只实现一个 shared primitive 或一个应用壳改动，附中英/键盘/窄屏测试；
3. 对每个页面说明“哪些事实来自 API、哪些状态还不能显示”；
4. 不改变 Docker、NixOS、真实域名、身份提供商或生产服务，除非用户单独授权；
5. 通过现有设计、i18n、安全和浏览器门禁后，才进入下一页面。

这样可以让视觉升级保持可回滚、可审计，并且不会牺牲现有 Human/Agent 授权、审计和
未知写入保护。
