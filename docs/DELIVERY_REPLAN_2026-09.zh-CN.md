## 1. 固定范围：三条既有产品线，加一条应用 API

| 产品线 | 本轮约束 | 允许的新增与收敛 |
| --- | --- | --- |
| Human Mail | 保留邮箱、登录、读取、草稿、发送、授权与交互语义，不因验证码功能改为另一种产品 | 修复已发现的视觉/功能回退；在兼容测试下拆分内部模块 |
| Agent Mail | 保留机器身份、独立处理状态、租约、Webhook/SSE、策略、沙箱与受控发信 | 复用通用基础能力，但不让业务应用冒用 Agent，也不削弱 Agent 专属策略 |
| 企业管理 | 保留组织、域名、角色、审批、审计、保全和留存治理 | 增加“应用接入”：应用、凭据、验证码策略、模板、发件身份与投递查询 |
| Application API | 新增独立的业务应用服务身份与邮件验证码用例 | 提供签发、校验、受控重发、取消及最小状态查询；由同一企业控制平面管理 |

沿用 Rust 后端、PostgreSQL 优先、React/TypeScript、Docker、多语言 README。
验证码应用不是第三套邮箱 UI；Human/Agent 的公共契约不因新增应用身份而自动扩大。

原有未完成的附件、线程、HA 等企业长期目标不删除，也不混入验证码首个交付切片；需要在各自
原计划中继续跟踪。不得把本次阶段验收重新命名为完整 Enterprise GA。

## 2. 已有能力与缺口

2026-09-19 源码核对结果：

- 已有 `docs/openapi-v2.yaml`，邮件、Agent、管理和审计 API 均非从零开始。
- 尚未发现独立的应用邮件验证码签发/校验契约和状态机；OIDC authorization code 不属于该能力。
- 已有 durable submission、幂等、Worker 租约、投递对账、事务型 Outbox 和不可变审计可参考。
  **可复用机制不等于可直接复用 Human/Agent 的业务权限入口。**
- 控制面 `apps/copilotmail-control/src/lib.rs` 约 17,662 行，Mail `App.tsx` 约 1,632 行，
  PostgreSQL adapter 也集中在大入口；新增功能前先建立可独立测试的边界。
- 当前工作区有大量未提交与未跟踪改动；R0 必须确认来源和形成可追溯候选版本，不能丢弃现有成果。
- 8 月 24 日的 411 条 Web 单元测试、109 条浏览器测试和 103 张截图是历史证据。
  已接受的桌面截图仍有按钮样式退化；快照比较通过不是视觉质量签字。
- 9 月 19 日状态核查中的设计、文档、i18n、审计静态门禁通过，只证明各自静态检查范围；
  真实邮件、企业 IdP、最新数据库迁移及 NixOS Docker 运行态不能据此视为通过。

## 3. 新 API 的产品默认值

本轮按**托管邮件验证码**规划：应用后端请求签发，CopilotMail 生成并发送，应用后端再请求校验。
这比“仅提供一个发送任意验证码正文的接口”多包含完整生命周期与安全责任边界。

具体契约、状态机、数据和事务设计见
[应用验证码 API 设计计划](APPLICATION_VERIFICATION_API_PLAN.zh-CN.md)。

- 首版面向应用服务端，不在浏览器/App 包内分发机器凭据，不开放匿名公共发信。
- 用途登记可覆盖邮箱验证、注册确认、账户恢复和经风险评审的低风险邮件登录；业务账户存在性、
  登录会话签发、密码变更和业务授权始终属于调用应用。
- 不改变 CopilotMail 员工/管理员的企业 OIDC 与 MFA，不把邮件验证码宣传为高保证认证因子。
- 先交付邮件渠道与受控模板，不扩展短信、营销群发、任意 HTML/附件或万能认证平台。
- 若实际只需“应用自管验证码，平台代发”，应单独记录责任变更，再增加受控事务邮件 API；
  不在同一接口隐式混用两种安全模型。

## 5. 低耦合、高内聚的强制设计规则

### 5.1 模块组织

以下为目标职责，不要求一次创建全部新 crate；先按现有 workspace 中的业务模块拆分，只有存在
独立依赖/测试/发布边界时才拆 crate。

| 边界 | 拥有的责任 | 不得依赖或承担 |
| --- | --- | --- |
| `domain/application_identity` | Application 身份/生命周期、受控能力 | HTTP、SQL、Agent 处理状态 |
| `domain/verification` | 挑战状态、有效期、次数、绑定和合法转换 | 系统全局时钟、网络、PG、邮件正文/UI |
| `application/verification` | 签发、校验、重发/取消用例，授权、事务编排 | Axum Request、SQLx 类型、SMTP/JMAP 客户端 |
| `application/verification/ports` | 按用途定义 Clock、Secret、Repository/UoW、Transport、Template 边界 | 全局 Service Locator、继续膨胀的万能 Store trait |
| `postgres/verification` | SQL、约束、锁、幂等、配额与事务实现 | 重新定义领域规则、隐式访问其他应用资源 |
| `mail-engine` / crypto adapter | 公开协议、加密库和外部系统适配 | 注册/登录业务规则、HTTP 权限决策 |
| `control/http/{mail,agent,admin,verification}` | 路由、认证上下文提取、验证 DTO、错误映射 | 业务 SQL、验证码状态机、无限重试、跨用例编排 |
| `worker/verification_dispatch` | 调度、租约、超时、对账、结果落账 | 持有事务调用远端、绕过过期/撤销/配额规则 |
| 前端 feature/controller/view | 用例交互、状态控制、纯呈现分别组织 | 组件内复制后端授权规则，或 UI 直接操作 Secret |

事务可以跨同一个 PG 数据库中的业务记录、幂等记录、配额、Audit 和 Outbox；模块化不要求把
同一用例拆成多个无法原子提交的数据库或微服务。保持模块化单体优先。

### 5.2 可独立测试与注释

- 地址验证、输入归一化、用途策略、状态转换、配额决策、模板变量、错误映射、重试计划等可确定性
  测试的模型必须提取为有类型的纯逻辑；时钟、随机性与外部依赖显式注入。
- 每个公共用例和安全相关函数都有输入/输出、前置条件、失败路径、时间来源、幂等/事务语义说明。
  注释重点解释“为什么不可绕过”，不重复每一行代码的语法。
- 不为测试而把所有私有函数公开；纯规则单元测试、模块私有测试、公开用例契约测试各司其职。
- R1 建立文件/函数复杂度基线。新增非生成生产文件超过 600 行、单函数超过 80 行，或圈复杂度
  超过 10 时必须触发设计复核；这些是审查触发线，不是拆文件绕过门禁的目标。旧文件先禁止继续
  无解释增长，再按业务职责偿还债务；测试、迁移和声明式数据单独计量。
- 领域/用例模块不得新增 HTTP/PG/邮件 adapter 的反向依赖；架构检查同时覆盖直接和传递依赖。

## 6. 事务设计：必须证明的不变量

| 不变量 | 设计/数据库保障 | 必须验证的竞争或故障 |
| --- | --- | --- |
| 没有未落账的业务成功 | 业务写入 + 幂等结果 + Audit + Outbox 同一 PG 事务，提交后才返回成功 | Audit/Outbox 失败、COMMIT 响应丢失、进程中断 |
| 一个验证码挑战最多成功一次 | 固定锁顺序、当前状态/版本条件更新、验证结果唯一约束 | 两个并发正确校验、成功后重放、过期瞬间竞争 |
| 限流不会被多副本绕过 | PG 权威时间和原子共享配额，跨挑战/用途的累计预算 | 并发签发、重发、新 flow、新幂等键、窗口边界 |
| 已撤销权限不能被旧快照重新授权 | 在用例事务内最终核验应用/凭据/策略版本和精确绑定 | 校验途中暂停应用、轮换/撤销、旧 Token 重放 |
| Worker 失效后不能覆盖新结果 | 持久租约 + fencing token + 条件更新 | 超时回包、旧 Worker 恢复、多个 Worker 领取 |
| 外部结果未知不变成重复投递 | 已提交 intent、稳定相关 ID、精确对账、有限恢复 | 发信被接受后断网、远端查询不可用、重启 |
| 验证成功不等于业务动作成功 | 验证收据绑定应用/用途/flow；业务应用本地事务内去重收据并变更状态 | API 成功后应用崩溃、回包丢失、重复回调 |

禁止“开始事务 → 发邮件 → 提交”及“先发邮件 → 再创建验证码”。邮件服务不能加入 PG 原子事务；
跨系统采用持久意图、Outbox、幂等、结果对账与恢复流程，不承诺网络层绝对 exactly-once。
数据库并发控制不能仅用“先 SELECT 再 INSERT”推断唯一性，也不能假定普通事务自动消除写偏差。
锁/隔离级别及有界整事务重试须逐用例说明，依据
[PostgreSQL 17 事务隔离文档](https://www.postgresql.org/docs/17/transaction-iso.html)。

## 7. 所有功能的测试与证据要求

### 7.1 建立函数/能力到测试的可追踪矩阵

R0 建立、各阶段补齐 `quality/function-test-matrix.yaml`（拟新增机器可读清单），固定字段为
`capability_id`、`module`、`entrypoints`、`risk`、`invariants`、`cases`、`test_refs`、`environment`、
`evidence_ref`、`candidate_revision`、`owner` 和 `review_status`。cases 明确正常、边界、拒绝/失败、
事务与并发；覆盖范围是 Human、Agent、Admin、Application API 以及底层模块，不只是验证码。

R0 由主执行者负责 schema/能力清单，各模块实现者维护映射，R7 复核者检查遗漏和证据。拟新增
`scripts/check_function_test_matrix.py`，在 CI 校验字段、能力 ID 唯一性、符号/测试引用和必测类别，
再关联实际测试清单、覆盖报告与候选版本结果；缺少 owner、失效引用、关键能力无负向/事务测试或
以 skipped/未执行替代通过均阻断对应阶段。脚本存在性本身不是测试充分性证据。

| 层级 | 必测内容 | 完成口径 |
| --- | --- | --- |
| 纯领域/规则 | 所有状态转换、边界值、未知枚举、过期/次数/绑定、不合法输入；属性/模型测试 | 无网络/数据库即可独立运行；关键不变量有反例测试 |
| 应用用例 | 正常、每个依赖失败、授权撤销、幂等回放/冲突、事务调用顺序 | Fault-injection ports 能证明失败不会继续发送或返回成功 |
| PostgreSQL | 唯一/外键/CHECK、事务回滚、锁竞争、隔离重试、数据库时间、迁移/恢复 | 可丢弃的真实 PG 17，多连接/多进程执行；不能只用内存替身 |
| HTTP/契约 | DTO、错误码、scope、租户/应用隔离、body 大小、敏感信息、重试头 | OpenAPI 与实现同步，所有新增 operation 有成功/失败契约 |
| 外部适配/Worker | 断网、超时、响应未知、重复/乱序事件、租约过期、重启/死信 | Fixture 故障测试 + 真实邮件引擎验收分别记录 |
| 前端 | 人员/Agent 原有交互、应用治理、并发响应、未知状态、键盘/触点/双语 | unit + E2E + 人工视觉检查；不得只更新截图使比较通过 |
| 集成与性能 | 两应用/两租户并发、验证码正常/过期/错误/重发、真实收发、配额、数据库故障、恢复 | 有实际环境、版本、执行时间、数据集与阈值；未执行项不算通过 |

新增/重构的验证码关键逻辑拟设行覆盖率 ≥95%、可测分支覆盖率 ≥90%；安全决策、状态转换及
事务失败路径必须 100% 有具名测试，关键不变量增加 mutation/property testing，防止“测到了但没断言”。
既有代码先测基线并补齐功能矩阵，覆盖率不得下降；覆盖工具不支持的指标须明确报告，不能当作 0 缺口。
R0 须选定可运行的覆盖工具与基线；若关键分支指标不可用，必须在 R7 前提供经独立复核的等价路径
证据和明确接受记录，缺失时仍阻断放行，不能只在日志中写“工具不支持”。
覆盖率目标不是“无漏洞保证”，也不得把纯转发/生成代码和业务规则混在一起刷数字。

### 7.2 保留并扩展现有门禁

- Rust：fmt、Clippy `-D warnings`、workspace tests、架构门禁、审计治理；新增模块单独测试和覆盖报告。
- Web：类型检查、Vitest、生产 build、Bundle budget、Playwright、i18n、设计治理、人工审图。
- 真实依赖：现有 PG/MinIO ignored 场景必须在专用 CI/隔离环境显式执行，并补验证码并发/故障场景。
- 契约与安全：OpenAPI/AsyncAPI 一致性、认证负向、秘密扫描、依赖/许可证、镜像漏洞、SBOM。
- 部署/文档：Compose 安全、迁移升级、备份恢复、健康检查、持久化重启、文档链接、中英文接入示例实跑。
- 新审计动作必须同时更新领域目录、SQL catalog、应用生产者和治理脚本/测试；事件成功须与业务同事务。

## 8. 最终代码质量审查（所有功能完成后）

R7 必须生成独立于实现说明的最终报告，并由另一检查视角复核、主执行者实际重验。
审查对象是可追溯版本的全部生产源码、数据库迁移、容器配置、前端、SDK/示例和文档，不局限于新增 diff。

1. 架构：依赖方向、领域内聚、模块可测试性、大函数/大类、重复规则、过度抽象和死代码。
2. 行为：Human/Agent 兼容、业务用例完整性、状态机、错误恢复、已知功能缺口和 UI 真实性。
3. 安全：跨租户/跨应用、scope、认证撤销、敏感字段、密钥轮换、暴力猜码、邮件轰炸和模板注入。
4. 事务：检查后使用竞争、半状态、双写、幂等、配额竞争、Worker fencing、回包丢失及跨系统收据消费。
5. 测试：逐能力/函数矩阵、断言质量、边界与负向、mutation 存活项、真实依赖、无意义或跳过测试。
6. 运维：资源隔离、日志脱敏、告警、备份恢复、升级回滚、非 root、镜像来源和凭据恢复演练。

报告逐项写明严重度、证据、影响、责任人、修复任务、回归测试和复核结论。
阻断功能/数据完整性问题及 Critical/High 不得豁免发布；其余问题必须明确接受人与修复期限。
任何修复后重新执行相关模块、兼容矩阵和最终全量门禁，不能仅以“已改代码”关闭问题。

R7 开始前冻结候选版本标识，并把测试/覆盖/镜像结果绑定到它；修复后形成新候选并使旧签字失效。
触及共享认证、授权、事务、投递、Secrets、数据库 schema 或公共契约的修改必须重新执行全域
R7 审查，而不只是改动文件复核。仅局部展示/文档修复也要有独立影响分析、复核和最终全量门禁；
最终签字必须重新确认新候选版本所有审查域都有效，不能沿用旧版本的总体结论。

## 9. Docker 与用户测试边界

- 保留 Docker 交付；完整栈不能只以 UI 预览代替。明确区分 mock/沙箱、隔离集成、企业试用和生产。
- 不再依赖故障 WSL。目标 NixOS 承载其他生产应用时，先只读检查目录、磁盘、端口和资源，
  再由用户授权具体构建/运行窗口；不修改 NixOS 全局配置、不重启 Docker、不清理他人容器/卷。
- V2 Compose 必须显式指定版本与配置，不使用仓库根 V1 的默认启动方式；数据库/对象存储端口
  不向 LAN 发布。用户需要 LAN UI/API 时只在批准的网关端口监听 `0.0.0.0`，真实凭据通道使用 TLS。
- 仅使用专用试用应用、邮箱、域名和接收人做发信验证；不得以压测/验证码测试向真实用户批量发送。
- 交付包括：从零安装、配置/轮换、迁移、恢复、停止/回滚、告警、应用接入、幂等和故障处理手册。

## 10. 开发前与真实发信前需要补齐的输入

不阻塞当前规划和纯模块开发；进入相应实际集成前必须确认：

1. 首个接入应用、后端语言、用途，以及是否允许邮件登录/账户恢复。
2. 批准发件域名/地址、企业 IdP、试用收件箱和出站邮件能力。
3. 应用与租户的并发量、日额度、验证码延迟目标、错误预算和数据保留期限。
4. 密钥注入/轮换方式、负责审核用途和增额的管理员、紧急停用流程。
5. Docker 测试资源与允许端口、备份/回滚窗口、是否在专用测试机执行故障/压力测试。
