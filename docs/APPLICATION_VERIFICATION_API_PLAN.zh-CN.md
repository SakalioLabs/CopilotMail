## 1. 需求判断与安全边界

当前已有邮件/Agent/管理 OpenAPI，但没有独立的业务邮件验证码签发和校验。
`PrincipalKind::Service` 已有领域枚举，不代表应用认证可用：现有 `AuthenticatedPrincipalKind`
仅 Human/Agent，控制面认证器也只接这两类。必须补全 Service/Application 的认证、授权、迁移
与负向测试，不能复用组织 bootstrap 的 root service principal 或伪装成 Agent。

首版采用托管模式：CopilotMail 负责安全随机码、有效期、投递、尝试计数与一次性校验；调用应用
负责业务账户、预登录/操作会话、反机器人交互以及验证后具体业务动作。**只返回邮箱控制权的
验证结果，不自动创建账户、登录、重置密码或赋予业务权限。**

邮件地址确认与高保证认证应明确区分；NIST 对邮件作为带外认证因子有禁止性要求，同时明确
邮箱地址确认码不受该禁止条款影响。因此本能力不替代公司 OIDC/MFA，不宣称达到 AAL2，
账户恢复/邮件登录用途须由业务负责人单独接受风险。
[依据：NIST SP 800-63B-4 的带外认证说明](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)。

首版不包括短信、营销群发、任意正文/附件、魔术登录链接、浏览器直连机器 API 或管理后台查看验证码。

## 2. 责任与依赖边界

```text
业务应用的浏览器/客户端
  → 业务应用后端：会话/flow 绑定、账户规则、对用户的中性响应
    → CopilotMail Application API：应用认证、scope、用途与配额
      → Verification 用例：状态机、事务、验证收据
        → PostgreSQL：Challenge + 幂等 + 配额 + Audit + Outbox
          → Dispatch Worker：持久租约 → 邮件 adapter → 结果对账
```

- 验证码业务不依赖 Human 草稿、已读/星标或 Agent Claim/Ack/Nack；这些状态禁止联动。
- 复用现有密码学库、数据库事务基础、审计、Outbox、transport adapter 与对账模式。
- 新建验证码专属 dispatch intent；如抽取共用投递机制，必须留住 Human/Agent 的各自准入策略。
  不直接绕过原 `MailSubmissionService` 的身份限制，也不把验证码硬塞进某个人的私有草稿目录。
- 领域状态机、过期/次数规则、模板变量与重试计划可脱离 PG/网络独立测试。
- 所有邮件网络 I/O 都在短数据库事务之外，业务用例不依赖 Axum/SQLx/具体 JMAP 客户端。

## 3. 应用身份、授权和管理

### 3.1 身份模型

每个应用有独立 `application_id`、所属组织、绑定的专用 Service principal、责任人、生命周期
与单调配置版本。`active / suspended / retired` 不直接映射成在线/离线。
应用机器凭据仅供其后端使用，与 Human Session Cookie、Agent Token audience/能力明确分区。

优先使用 OAuth2 client credentials 下的 `private_key_jwt` 客户端认证和短期访问 Token；
复用密码学验证基础时，为 Application 增加独立 audience、主体类别与 scope 判定。
首版不增加一个长期全权 Bearer API key 作为临时捷径；mTLS 绑定按已有基础单独验收。

拟新增最小权限：`verification.issue`、`verification.verify`、`verification.read`、
`verification.cancel`；重发使用 `verification.issue` 并受原挑战和配额约束。
应用管理权限单独定义为 `application.manage` 与 `verification.policy.manage`，仅经授权的
Active Human 在 Admin BFF 下操作。既有 Owner/角色规则不能被应用自助提权绕过。

应用只可访问 Token 所绑定的组织/应用；客户端不能通过请求体选择 `organization_id`、
`application_id`、principal、From 或绕过策略的 TTL/次数。应用停用/凭据撤销必须在用例提交前
再次通过数据库权威状态核验，而不是只相信 Token 的尚未到期。

首版拟定角色映射：租户 Owner 可管理本租户应用；新增 Human-only 的 `ApplicationAdmin`
固定角色持有 `application.manage` 与 `verification.policy.manage`，授予/撤销继续经过既有
角色治理与权限提升审批。策略放宽的批准权与申请人隔离，不因持有此角色就允许自批。
其余既有角色不自动增加新权限。R2 必须把该映射落入权威角色目录、回填迁移与授权矩阵测试。

认证扩展同时执行双向拒绝矩阵：Human/Agent 凭据不能调用 Application self API；Application
凭据不能调用旧 Human 邮件、Agent processing、Admin/合规 API；应用 A 不能读取/校验应用 B 的
挑战；组织 A Owner 不能管理组织 B 应用。不得用“所有非 Human 都当作 Agent”这样的兜底分支。

### 3.2 治理能力

- 应用注册/暂停/退役、责任人、只展示公开 key ID/指纹的凭据轮换与撤销。
- 批准发件域名/地址、用途白名单、额度、模板版本和语言。
- 放宽权限/配额/发件域名需要受控审批；紧急暂停可由已有应急角色立即执行并审计，不能等审批
  才止损。只读凭据元数据不等于可读取 Secret。
- 只显示真实请求和投递证据、版本和安全错误；不显示明文验证码、码摘要、加密负载或任意收件人列表。
- 不因一个猜码攻击暂停业务用户的账户；锁定对象是挑战/验证窗口，业务账户策略仍由应用负责。

## 4. 拟新增 API 契约

以下路径均为计划，实施 R2/R3 时才写入并验证正式 OpenAPI。

| 方法与路径 | 请求要点 | 结果与副作用 |
| --- | --- | --- |
| `POST /api/v2/applications/self/email-verifications` | Header `Idempotency-Key`；body 含 `recipient`、登记的 `purpose`、应用后端生成的 `flow_id`、批准模板引用、`locale` | `202`：生成挑战、预留配额、写 dispatch/Audit/Outbox；仅返回挑战 ID、到期时间、冷却下界 `resend_not_before`、`queued` |
| `POST /api/v2/applications/self/email-verifications/{id}/verify` | 幂等键；body 含 `code`、原 `purpose` 与 `flow_id` | 同事务比较/计数/消费；正确返回最小验证收据，错误返回统一的无效结果；不回显验证码 |
| `POST /api/v2/applications/self/email-verifications/{id}/resend` | 幂等键；原 flow；不得更改地址、用途、模板或有效期 | 只在允许状态、冷却期及配额下新增一次 dispatch；不是自动重放原发信 |
| `POST /api/v2/applications/self/email-verifications/{id}/cancel` | 幂等键；原 flow | 原子取消仍 active 的挑战及尚未发出的任务；不保证撤回已在途邮件 |
| `GET /api/v2/applications/self/email-verifications/{id}` | `verification.read`，精确应用绑定 | 仅返回状态、到期、投递事实及当前 `can_resend` / `resend_not_before`；不返回码、收件地址、正文、可用于业务授权的验证收据 |

管理端另设组织内 Application、凭据元数据、Sender Profile、Policy/Template Version 的受控
管理路由；遵循当前 Admin BFF、Active Human、RBAC、CSRF 和审计约定，不把管理能力放到 self API。

### 4.1 请求/响应规则

- TLS，机器 API 不接收 Human Cookie；所有返回 `Cache-Control: no-store`。
- 严格 DTO、未知字段拒绝、请求体/字段长度限制。数字码作为字符串，保留前导零。
- `flow_id` 由业务后端用至少 128 位随机性生成并绑定用途、用户流程和目标地址，不能采信浏览器
  自由提交的 flow 与业务账户绑定。校验后同一 flow 不得被换绑成另一用户/操作。
- 地址解析复用受测 parser；仅做明确定义的域名 IDNA/大小写处理，保留 local-part 语义，
  不擅自移除点号、加号后缀或将全部地址无条件转小写。策略定义首版可接受地址语法。
- 从批准 Sender Profile 派生 From，模板必须是批准的不可变版本；不接受客户传入任意邮件头、URL、
  任意 HTML 或 `code` 模板变量。业务参数白名单、长度及转义均由模板 schema 控制。
- `401/403` 为认证/能力拒绝；不存在和跨租户/跨应用资源统一 `404`；幂等键不同 payload 为
  `409`；限流 `429 + Retry-After`；依赖故障返回稳定脱敏 `503`，不得泄露是否猜中。
- 对所属应用内的错误码、过期、已消费和锁定，verify 使用同一 `invalid_or_expired` 失败外形；
  详细原因只在受控最小审计中分层记录，不提供剩余尝试次数给匿名用户。
- 平台没有业务应用账户目录，不应替应用判断账号是否存在。应用公开入口对不存在/存在账户采用
  同样的中性文案与可比处理流程；必要的发信与风险控制在后端处理，防止枚举。

生成、安全保存、一次性使用、短有效期、限制猜测和中性账户响应采用
[OWASP Forgot Password 指南](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
中的通用安全原则；本方案具体 flow、收据和事务边界为项目设计，不是该指南已经实现的功能。

### 4.2 幂等与成功收据

幂等域固定为 `(organization, application, operation, key)`，使用数据库唯一约束。
请求指纹采用服务端带密钥摘要，特别是含六位码的 verify body 不得只做可离线枚举的普通 SHA-256。
同键同请求只恢复原业务结果，不重复发信/计费/扣次数；同键不同请求拒绝，入口速率限制仍生效。
重放仍须通过当前应用/凭据授权及收据有效期核验，不保证一份历史成功结果现在仍可授权。
幂等恢复窗口首版建议 24 小时。过窗后客户端不得继续重试写操作来猜原结果，而应查询精确 challenge
状态和本地业务操作账本；保留窗口内的旧 flow 不能重新签发，终态/已清理 challenge 不能再次消费。
flow 终态最小 tombstone 的保留期不得短于恢复窗口；已清理 challenge 按不可用资源拒绝。
不承诺幂等记录/tombstone 清理后仍能识别任意历史签发请求：接入应用必须持久化业务操作账本承担
长期去重，新业务操作使用新 flow/key，禁止用过窗写重试恢复旧操作。测试明确区分窗口内的原子去重、
窗口外的不可恢复响应和应用侧长期去重，不宣传无限期 exactly-once。

正确校验在 PG 原子产生唯一的不可变 `VerificationReceipt`，绑定：组织、应用、挑战、用途、flow、
批准策略版本、验证时间、收据到期时间，以及服务端的接收目标绑定引用。不是可转让的通用登录 Token。
默认收据有效期建议 5 分钟；业务应用只相信自己的服务器到服务器响应及本地已绑定 flow，
不接受浏览器自报 `verified=true`、另一应用的收据或只看状态查询就执行敏感动作。

首次 verify 回包丢失时，应用以同一幂等上下文恢复同一收据；不得用新幂等键触发第二次成功消费。
收据过期后不返回新的可用授权；历史状态为 verified 不等于收据当前可用。具体过期响应必须测试。

业务应用在**自己的数据库事务内**核对原流程/目标，检查收据有效性，以唯一收据 ID 去重，并完成
注册确认/账户变更。跨 CopilotMail 与应用数据库不能承诺一笔原子事务：已验码但业务落库失败时，
仅在收据仍有效时，以原收据和原业务幂等操作恢复；不得解锁旧验证码、重新消费、或更改收据绑定。

到期恢复规则必须显式实现：

- 应用本地事务已在有效期内提交，只是回包丢失：按本地唯一收据/业务幂等账本返回已经完成的结果，
  这不是到期后执行新授权。
- 应用事务未提交且收据已经到期：拒绝新的业务变更，旧挑战仍为 verified；用户重新启动一个新 flow
  并重新验证，仍受跨 flow 配额/猜码预算约束，不静默延长收据。
- 应用 COMMIT 结果未知：先按精确业务操作 ID/收据 ID 对账；不能因网络异常就新开操作或标记成功。
- 应用事务也要在持有必要锁后按自己的数据库时间检查收据期限；两端时钟同步/最大允许偏差纳入部署
  验收，时间可信度不足时不执行新的敏感动作。

服务器端示例必须覆盖上述三类恢复和到期边界；不承诺超过收据有效期仍可无感恢复业务变更。

## 5. 生命周期与默认策略

### 5.1 两个独立状态机

| 验证状态 | 合法变化/事实 | 禁止行为 |
| --- | --- | --- |
| `active` | 正确校验 → `verified`；到期 → `expired`；次数耗尽 → `locked`；取消 → `cancelled` | 仅因邮件 accepted/delivered 就验证成功 |
| `verified` | 已经产生唯一收据；只允许精确的幂等结果恢复 | 再次消费、重发、换绑或恢复 active |
| `expired / locked / cancelled` | 终态；新流程必须重新走授权、配额和签发 | 修改 expires_at、清零计数或重启旧任务使其有效 |

投递另行记录 `queued / dispatching / accepted / delivered / failed / unknown`。
`accepted` 仅是邮件引擎接受，`delivered` 仅在可信证据证明接收方服务器接受时使用，不等于阅读。
没有投递快照就显示未知/待确认；verification 不依赖一个伪造的“已送达”状态。

### 5.2 建议默认值（R0 冻结，不是已实施配置）

| 项目 | 首版建议 | 不变量 |
| --- | --- | --- |
| 随机码 | 6 位十进制，密码学安全随机，支持前导零 | 不使用时间戳、UUID 截取或有偏取模生成 |
| 挑战有效期 | 5 分钟；配置上限 10 分钟 | 从首次签发的数据库时间起算，不随重发/延迟投递延长 |
| 错误尝试 | 每挑战最多 5 次 | 并发原子扣减，重发不清零，重复同一幂等失败不重复扣减 |
| 显式重发 | 冷却 60 秒，每挑战最多 3 次 | 沿用同一码、同一挑战、原 expires_at；每次真实重发独立计配额 |
| 收件目标限额 | 建议每 60 秒最多一次投递请求、15 分钟最多 5 次；跨用途累计 | 不能靠新 challenge/flow/幂等键绕过；不以客户端 IP 参数为可信来源 |
| 猜码累计限额 | 除挑战上限，再按应用+目标设置跨 flow 的时间窗预算 | 建新挑战不能无限刷新猜码预算；不得据此锁定应用业务账户 |
| 应用/租户额度 | 上线前按容量签署，缺省不开放生产额度 | PG 跨副本共享；网关仅为附加防护，不作为唯一计数器 |

一个 `(租户, 应用, 目标, 用途, flow)` 同时最多一条 active 挑战。
同 flow 换目标或用途必须拒绝，不能把“邮箱变了”当作允许重新绑定原验证结果。
调用方若要新流程必须新建 flow，同时仍受跨流程的额度和失败尝试窗口约束。

显式重发在 dispatch 在途/结果未知时拒绝，并先对账，避免把网络失败误认为没发出。
重发使用同一码是本版明确选择：减少邮件乱序造成“新码旧码”混淆，不延长有效期、不重置次数；
终态后不能重发。同键网络重试不是显式重发。

`resend_not_before` 仅表示冷却期下界，不承诺到点就一定允许发送。状态查询中的 `can_resend`
是当前状态/配额快照而非预留许可；客户端在显式重发前可查询，最终仍由 resend 事务重新判定。
冷却/配额不足返回 429；在途或未知返回稳定 409；到期/终态拒绝，不鼓励无休止请求重发。

## 6. PostgreSQL 与秘密存储设计

拟新增逻辑表/聚合（最终命名与 migration 编号在实现时分配，不能预占现有 0059 等编号）：

| 聚合/表 | 责任 | 约束 |
| --- | --- | --- |
| Applications / credentials / sender profiles | 应用与 Service principal、授权发件来源、凭据及版本 | 所有关系带租户/应用复合外键；不能关联 root bootstrap 身份 |
| Verification policy/template versions | 批准用途、限额、模板 schema 与版本 | 版本不可变，激活/撤销受审计，签发后固定引用 |
| Verification flows | 串行化同 flow 的签发/取消/校验，当前挑战指针 | 唯一范围约束；先确保行存在再加锁，不能对不存在的行假装已锁定 |
| Verification challenges | 状态、码认证摘要/nonce/key ID、expires_at、次数、版本 | 合法转换/CAS、范围绑定、计数非负、终态不得重开 |
| Verification secret payloads | 发信必需的最小地址+码+模板参数密文 | AEAD、用途/租户/挑战作为认证上下文、独立密钥、TTL 和受控清理 |
| Verification dispatches | 独立发送意图、状态、有限重试、租约/fencing、精确远端引用 | 同次调度去重，不包含日志可见正文，旧租约禁止覆盖新状态 |
| Verification attempts / receipts | 最小尝试证据、唯一成功收据 | 不可变；成功收据与挑战唯一；不保存可枚举的原始码摘要 |
| Verification idempotency / rate windows | 同操作幂等记录、跨副本配额与失败预算 | 唯一键、原子计数、权威时钟、明确清理和重放窗口 |
| 既有 Audit / Outbox | 治理证据和异步唤醒 | 与业务同连接同事务；Outbox 仅引用 opaque ID，不携带验证码明文 |

验证码空间很小，校验材料采用带服务端秘密的 HMAC/等效受审查构造，绑定租户、应用、挑战、用途、
flow 和 nonce；密钥不与数据库备份一起保存，比较使用恒定时间基础函数。加密密钥、摘要密钥、
请求指纹与查找索引密钥要域分离，密钥版本/轮换与恢复方案需要测试，不自创密码学算法。

**异步发信不能只留不可逆摘要。** Worker 还需取得验证码，所以另存短期加密的最小 dispatch
负载；仅 Worker 可解密。为支持同一码重发，必要密文最多保留至挑战终态/到期及受控在途处理结束，
之后清除（含死信/队列引用），不能永久留在不可变审计中。清理敏感负载不等于删除审计证据。
接收方邮箱和邮件引擎会持有实际邮件内容，这不在“控制面不存明文码”的保证范围内。

地址在需要精确投递的位置加密；按域分离 HMAC 建立查找/配额引用。日志、Trace、指标、异常、
Audit、URL 和 Webhook 不含完整地址、code、body、credential 或可暴力枚举的裸 hash。
指标不得以地址/challenge/flow 作高基数标签。Secrets 注入、缺失、轮换、备份与恢复均需运行手册。

## 7. 事务与外部 I/O 的具体边界

### 7.1 签发/显式重发

1. HTTP 层做格式/大小检查和认证；用例开启短事务并按固定顺序锁应用/flow/配额。
2. 在锁取得后使用数据库当前权威时间，复核应用、凭据、用途、模板/发件配置版本和幂等结果。
3. 原子预留配额，创建 challenge（或复核原挑战重发资格）、密文负载引用、dispatch intent、
   幂等结果、最小 Audit 与 Outbox。任一步失败全部回滚，不发送邮件、不返回已排队。
4. COMMIT 成功后返回 202；提交响应未知时恢复精确幂等结果，不能直接创建第二个挑战。

### 7.2 Worker

1. 短事务领取持久租约，检查 fencing token、挑战仍 active/未过期、应用/发件来源仍获准，
   标记 dispatching 并落审计/事件；然后提交。
2. 领租约事务提交后，在实际网络发信前检查剩余时间；依据最近取得的 DB 时间与单调耗时计算
   `send_deadline = min(challenge.expires_at, lease_expires_at)`，时间依据不可靠或预算耗尽时不发起调用。
   在事务外用固定相关 ID 调用邮件 adapter；首版单次调用最多 10 秒，且不得超过剩余预算。
3. 新短事务保存精确结果与 Audit/Outbox；晚到或旧租约响应只能按受控证据规则记录，不能恢复
   已取消/已验证挑战，也不能覆盖新 Worker 权威状态。
4. 若可能已被远端接受却丢回包，则进入 unknown，仅查询同一远端身份；不能证明未发送时不
   自动换 ID 重投。首版主动对账采用有抖动的退避，最多 6 次且不晚于 challenge.expires_at；
   每次查询同样有时间预算。预算耗尽后停止主动处理，保留 unknown 投递事实和超时审计，
   不伪造 failed。挑战到期后禁止校验/重发，允许用户按配额启动新 flow；迟到的可信投递证据
   可追加，但不能重开挑战。后台过期清理延迟不影响 API 按数据库时间即时拒绝。

权限/取消检查与外部发信之间无法绝对原子：已进入网络的邮件可能在取消或停用后到达。
对外保证的是取消后不再启动新的获准 dispatch、校验拒绝无效挑战，而不是撤回已经在途的邮件。
本地调用超时也不能保证远端停止接受，因此邮件到达延迟没有由本系统保证的硬上界；过期邮件里的码
不可用。Worker 的调用/主动恢复预算可测，远端 SMTP 到达时间不能伪装成相同保证。

### 7.3 校验与消费

1. 锁应用授权版本、flow、挑战和相应次数窗口；核对租户/应用/用途/flow 和幂等指纹。
2. 锁后再取数据库当前时间，不能用事务开始时固定的时间判断等锁期间已经过期的码。
3. 码错误：原子累计失败次数/预算、必要时转 locked，并记录幂等失败结果与最小审计。
4. 码正确：以 active/版本/到期条件更新为 verified，并插入唯一收据、幂等成功结果、Audit/Outbox。
5. 仅 COMMIT 成功后披露结果；审计或数据库失败时返回中性服务错误，不能泄露“其实猜对了”。
   网络响应丢失用原幂等键恢复；新键不得对已消费挑战再产生成功。

使用行锁、唯一约束和条件更新；必要时 Serializable 并对序列化/死锁进行有界整事务重试。
禁止在事务重试体里发送邮件或执行不可重复外部效果。
[依据：PostgreSQL 17 事务隔离与重试语义](https://www.postgresql.org/docs/17/transaction-iso.html)。

## 8. 必须通过的测试清单

| 类型 | 核心场景 | 必须证明 |
| --- | --- | --- |
| 规则/属性 | 码格式与随机源失败、TTL、边界秒、用途/flow/地址绑定、模板变量、终态 | 纯模块独立测试；非法状态不可到达；不得以统计“看起来随机”替代安全 RNG |
| 并发签发 | 多连接同幂等键、同 flow 不同键、不同 flow/用途同时抢配额 | 一个合法挑战/每次合法 dispatch 只落一次，配额不超卖 |
| 并发校验 | 多个正确请求、正确/错误同时到达、最后一次失败与正确竞争 | 最多一次状态消费；原幂等重放可恢复收据，其他请求不能新增成功 |
| 重试与猜码 | 同键失败重试、同键改码、新键/新 flow/重发 | 不重复扣同次失败、不泄露正确性、不清零累计预算 |
| 时间与撤销 | 等锁时到期、应用暂停、凭据撤销、模板/发件配置失效、进程时钟偏差 | 以锁后 DB 时间和权威版本判定，不接受过期/撤销上下文 |
| 投递恢复 | DB 提交前后崩溃、邮件接受后断线、结果写入失败、重复/乱序事件、租约过期 | 无未落账发送、无盲目重投、旧 Worker 不覆盖新结果、状态不倒退 |
| 重发/取消竞争 | resend vs verify/cancel/expiry/unknown | 次数不重置、TTL 不延长、终态不复活；已在途邮件边界如实表达 |
| 隔离与输入 | 两租户/两应用/两凭据、Human/Agent → Application、Application → Human/Agent/Admin 的双向路由矩阵、角色授予、自审批、Header/模板注入、超大 body | 默认拒绝，无跨范围读写、无未授权 From、无验证码/地址/Secret 泄漏 |
| 应用消费 | 验码成功回包丢失、业务落库失败、重复收据、换 flow/用途/目标、收据过期前后、业务 COMMIT 结果未知 | 应用本地事务去重并只执行原业务操作；有效期内已提交则恢复原结果，否则到期重启 flow；不以验证状态查询当授权 |
| 运维/生命周期 | 密钥轮换、密文到期/死信清理、停机恢复、迁移/备份恢复、容器重启 | 秘密生命周期受控；恢复后不激活已终态挑战或丢失审计链 |
| 兼容/体验 | Human Mail、Agent workflow、管理审批/审计、应用页面双语/键盘 | 既有契约与隔离不回退；没有假计数、占位成功或明文码调试入口 |

随机/时钟替身仅用于单元测试；故障 transport 仅用于测试构建，生产无可切换的返回验证码后门。
所有纯规则、公共用例、SQL 约束和 worker 失败分支纳入函数/能力测试矩阵及 R7 最终总审查。
真实发送只在批准的隔离域名和收件箱执行；压测使用隔离接收器，不轰炸第三方邮箱。
